# OSS Growth & External Validation

The project should earn attention through useful evidence, not manufacture social proof.

## Priority order

1. reproducible technical result;
2. external users who successfully run it;
3. issues that reveal real-world failures;
4. outside reproductions;
5. contributors;
6. stars/forks as secondary signals.

## 13-week adoption targets

These are directional rather than guaranteed:

- first 10 external users who successfully run an experiment;
- first 3 independent reproduction reports;
- first external issue based on a real run;
- first external pull request or benchmark contribution;
- 100 organic stars as an early signal;
- 300–500 organic stars as a strong stretch signal.

Stars are not allowed to become the core success metric.

## Support-program strategy

Once the repository has:

- a real release;
- reproducible results;
- active maintenance;
- external usage evidence;

then evaluate applications to programs that support important open-source maintainers/projects, including relevant OpenAI or Anthropic programs if eligibility and licensing align at that time.

Do not submit an empty repository and ask institutions to imagine its future greatness on our behalf.

## Launch assets for v0.1

Prepare:

- concise README with one honest headline result;
- reproducible benchmark table;
- one architecture diagram;
- one quality-vs-memory frontier visualization;
- install/run example;
- limitations section;
- release artifact/model link where licensing permits;
- technical write-up explaining what was tried and what failed.

## Community standard

External criticism is evidence.

If someone reproduces a failure:

1. thank them;
2. preserve the failing configuration;
3. reproduce it;
4. fix the method or narrow the claim;
5. never erase the problem because it harms the launch narrative.
